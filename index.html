Overview

Why index a genome at all?

Aligning millions of short reads against a reference genome by scanning the genome once per read is hopeless: a single pass over the human genome costs about 3·109 character comparisons, and read sets contain 107–109 reads. The fix is to pre-process the text once into an index, after which every pattern is located in time proportional to the pattern length, independent of the genome length.

All four structures shown here index the same object — the set of all suffixes of T — and differ only in how that set is represented:

  • Suffix trie: all suffixes as explicit character-by-character paths.
  • Suffix tree: the same paths with non-branching runs collapsed.
  • Suffix array: only the sorted start positions of the suffixes.
  • FM-index: the BWT plus two small rank tables, from which the same search is done backwards without storing suffixes at all.

The sentinel $, appended to T and defined to be smaller than every other symbol, guarantees that no suffix is a prefix of another. That makes every suffix end in its own leaf and makes rotations sort exactly like suffixes.

Index comparison

How to read this table

n = |T$|, m = |P|, occ = number of occurrences, σ = alphabet size.

  • Suffix trie: Θ(n²) nodes in the worst case. For the human genome this is roughly 1019 nodes — purely a teaching device.
  • Suffix tree: exactly n leaves and at most n−1 internal nodes, so O(n) nodes; but with child pointers and edge labels it costs ~15–20 bytes per base, i.e. tens of gigabytes for a mammalian genome.
  • Suffix array: n integers, 4–8 bytes per base, and O(m log n) search. Adding the LCP array brings it back to O(m + log n).
  • FM-index: the BWT is as compressible as the text, and with sampled Occ checkpoints and a sampled suffix array the whole index for a human genome fits in a few gigabytes. This is what Bowtie, BWA and HISAT use.

The "space (this input)" column counts actual objects built in this page, so you can watch the trie explode while the other three grow linearly.

Space figures are counted for this concrete input: trie and tree node counts are exact, the suffix array stores n integers, the FM-index stores the BWT string plus the C and Occ tables.

Suffix trie

Every suffix of T$ is inserted character by character. Leaves are labelled with the start position of the suffix they spell. The path matching the pattern P is highlighted.

What is a suffix trie?

A trie (from retrieval) is a rooted tree in which every edge carries one symbol, so each node corresponds to the string spelled on the path from the root. The suffix trie of T$ is the trie containing all n suffixes.

Construction: take each suffix in turn and walk down from the root, creating a child whenever the needed symbol is missing. Because $ occurs only once, every suffix ends in a distinct leaf, which is labelled with its start position in T.

Searching P: spell P from the root. If you get stuck, P does not occur. If you arrive at a node, every leaf below it is one occurrence, so the number of matches equals the number of leaves in that subtree. The highlighted path shows exactly this walk for the current pattern.

Key insight: every substring of T is a prefix of some suffix, so every substring is spelled by a path from the root. Searching becomes tree navigation in O(m) steps.

Cost: the suffixes have total length n(n+1)/2, and shared prefixes are the only savings, so the trie has Θ(n²) nodes in the worst case (try AAAAAA). This is why the compressed version on the next tab exists.

Suffix tree

The suffix trie with every non-branching path collapsed into a single edge. The tree has exactly n leaves and fewer than n internal nodes, so it needs O(n) space instead of O(n²).

What is a suffix tree?

A suffix tree is a suffix trie in which every chain of nodes with exactly one child is merged into a single edge labelled with the whole substring. Compare the two drawings: the paths are identical, only the number of nodes differs.

Why it is O(n): after compression every internal node branches, so it has at least two children. A tree with n leaves in which every internal node has ≥ 2 children has at most n−1 internal nodes — regardless of the text. Storing edge labels as (start, end) offsets into T rather than as copied strings keeps each edge to O(1) space as well.

Searching P: follow edges from the root, matching P against whole edge labels; the walk ends either inside an edge or on a node. All leaf labels below that point are the occurrence positions, giving O(m + occ) after construction.

Vocabulary: the string depth of a node is the length of the string it spells (not its depth in the drawing). Internal nodes correspond exactly to substrings that occur at least twice and are followed by at least two different symbols — these are the right-branching repeats, which is why suffix trees solve repeat finding, longest common substring and maximal-exact-match problems so directly.

Construction: this page compresses the trie, which is simple but quadratic. Ukkonen's algorithm builds the same tree in O(n) time and is the standard method; the result is identical, so nothing here depends on that choice.

Suffix array

The start positions of all suffixes, sorted lexicographically. It is the leaf order of the suffix tree. Matches of P form one contiguous block, found by binary search.

What is a suffix array?

SA is the permutation of the positions 0…n−1 that sorts the suffixes of T$ lexicographically: SA[i] is the start position of the i-th smallest suffix. Nothing else is stored — the suffixes themselves are read back from T on demand.

Relation to the suffix tree: if children are ordered by their first symbol, then reading the leaves of the suffix tree from left to right gives exactly SA. Compare the leaf labels on the previous tab with the SA vector below.

Construction: this page simply sorts the position array with a general-purpose comparison sort, which is O(n² log n) in the worst case but perfectly clear. Production tools use O(n) algorithms (DC3/skew, SA-IS) or O(n log n) prefix doubling; the resulting array is the same.

Sorted suffixes

How to read this table, and what LCP is

rank i is the row index, SA[i] the start position in T, and the last column shows the suffix beginning there. The suffix column is for illustration only; it is not part of the index.

Why search works: all suffixes that start with P are lexicographically adjacent, so the occurrences of P form one contiguous block of rows. Two binary searches find the first and last row of the block, each comparison costing up to m symbol comparisons — hence O(m log n). Highlighted rows are the block for the current pattern.

LCP[i] is the length of the longest common prefix of the suffixes at ranks i−1 and i, with LCP[0] = 0 by convention. It measures how much of the previous row the current row repeats, so tall LCP values mark repeats in T.

LCP values correspond to the string depths of the internal nodes of the suffix tree: the LCP of two adjacent leaves is the depth of their lowest common ancestor. Consequently SA + LCP can emulate a suffix tree traversal, and the binary search can be sped up to O(m + log n). Kasai's algorithm computes LCP in O(n) from SA; this page uses direct comparison, which is enough at these sizes.

Burrows–Wheeler transform and FM-index

Sorting all rotations of T$ gives the BW matrix; its last column L is the BWT. The FM-index adds the C table and the Occ table, which together make backward search possible without the matrix.

What is the BWT, and why is it used for read mapping?

The Burrows–Wheeler transform is a reversible permutation of the symbols of T$. It was invented for compression: it groups symbols that appear in similar contexts, producing long runs of equal symbols (see the run count above) that compress extremely well.

Two properties make it an index rather than just a compressor: it is invertible, so the text need not be stored separately, and it supports backward search, so patterns can be located directly in the transformed string. An FM-index (Ferragina–Manzini) is the BWT plus the small auxiliary tables C and Occ. This combination is the core of Bowtie, BWA and HISAT.

BWT string L

What L and F are

L (last column) is the BWT itself: for each sorted rotation, the symbol that precedes its starting position in T, i.e. L[k] = T[(SA[k] − 1) mod n]. So L lists the preceding symbols of all suffixes, ordered by the suffix that follows them.

F (first column) is simply all symbols of T in sorted order, so it is fully described by the C table and needs no storage.

Only L is kept; F is reconstructed, and the text itself can be discarded.

Burrows–Wheeler matrix

How the matrix is built and what the LF property means

Construction (conceptually): write down all n cyclic rotations of T$ and sort them lexicographically. The last column of the resulting matrix is the BWT.

Shortcut used here: because $ occurs exactly once and is the smallest symbol, no rotation can wrap past it during a comparison, so rotations sort exactly like suffixes. Row k is therefore the rotation starting at SA[k], and the matrix is never materialised in a real implementation — it is shown here only for teaching.

Last-to-first (LF) mapping: the i-th occurrence of a symbol c in L and the i-th occurrence of c in F denote the same position of T. Reason: rows containing c in L are sorted by the suffix that follows that c, and rows starting with c in F are sorted by the suffix that follows that same c — the relative order is identical. The LF column gives, for each row k, the row where L[k] reappears in F, computed as LF[k] = C[L[k]] + Occ[L[k]][k].

Repeatedly following LF from the row of $ walks through T backwards; this is exactly the reconstruction shown at the bottom of the page, and the same identity drives backward search.

C table

What C[c] is

C[c] is the number of symbols in T$ that are strictly smaller than c, i.e. the index of the first row whose first column equals c. Since F is sorted, the block of rows beginning with c is exactly [C[c], C[c] + count(c)).

C has only σ entries (five for DNA with a sentinel), so its cost is negligible; it is what makes column F unnecessary to store.

Occ table

What Occ[c][i] is, and how real indexes store it

Occ[c][i] (also written rankc) counts the occurrences of symbol c in the prefix L[0…i−1], i.e. in the first i rows. Row i = 0 is all zeros, and row i = n gives the total number of occurrences of each symbol in T$.

This single primitive — "how many c's occur before row i?" — is what makes backward search work in constant time per pattern symbol.

In practice: a full table needs σ·(n+1) counters, which would dwarf the text. Real FM-indexes store checkpoints every 64–512 rows plus a bit-packed BWT, and count the remaining symbols on the fly with word-level popcount operations. That keeps the lookup O(1) while adding only a small fraction of the index size.

Backward search for P

How backward search works, step by step

The algorithm maintains a half-open interval [sp, ep) of matrix rows whose rows begin with the suffix of P processed so far. It starts with the full range [0, n) and consumes P from right to left, one symbol per step:

sp ← C[c] + Occ[c][sp]    ep ← C[c] + Occ[c][ep]

Interpretation: among the current rows, keep those preceded by c (that is the Occ part), and map them into the block of rows starting with c (that is the C part) — the LF mapping applied to a whole interval at once. Prepending c to the matched suffix thus takes O(1) time.

If sp ≥ ep the interval is empty and P does not occur; the search stops early. Otherwise, after all m symbols, ep − sp is the number of occurrences — obtained without ever looking at the text, in O(m) total time regardless of genome size.

Reporting positions still needs SA[k] for each row k in the interval. Storing the full suffix array would defeat the purpose, so implementations sample it (e.g. every 32nd entry) and walk LF until a sampled row is reached, trading a little time for a large space saving. Reconstruction of T by LF mapping

How the text is recovered from L alone

Start in the row k whose L entry is $; L[k] is then the last symbol of T$. Apply k ← LF[k] and output L[k] again, prepending each symbol. After n steps the original T$ has been rebuilt from the BWT alone, which proves the transform is lossless — and explains why the original text does not need to be stored next to the index.
